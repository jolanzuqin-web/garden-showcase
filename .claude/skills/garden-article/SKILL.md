# Статья об агротехнике для posadu.ru (мультиагентный пайплайн)

Раньше один агент делал всё подряд: искал факты, писал, пересобирал. Теперь
за каждый этап отвечает отдельный субагент с ограниченным набором
инструментов — это структурно не даёт, например, писателю сослаться на
источник, которого не проверял исследователь. Коммит — отдельно (скилл
`garden-release`).

## Пайплайн

Вызывать субагентов через `Agent` строго по порядку, передавая результат
предыдущего шага как вход следующему:

1. **`garden-researcher`** — вход: тема (+ культура/регион, если есть).
   Выход: JSON `{ topic, tezisy, spornye_momenty }` с источниками на каждый
   тезис.
2. **`garden-agronomist`** — вход: JSON от `garden-researcher`. Выход: JSON
   `{ approved_tezisy, rejected_tezisy, climate_check_notes }` — проверены
   источники и сверка с климатическим отчётом проекта.
   - **Автовозврат на переисследование.** Если `rejected_tezisy` не пустой и
     без него статья не складывается (нет фактов на ключевую часть темы,
     например срок или норму нечем закрыть) — вызвать `garden-researcher`
     повторно, вложив в запрос конкретную причину отклонения из `reason`
     (например: «предыдущий тезис про сроки не подтверждён источником, найди
     точный срок с реальной ссылкой» или «нужен источник конкретно для
     Северо-Запада, не средней полосы») и пропустить обновлённый ответ через
     `garden-agronomist` заново.
   - Не более 2 таких кругов на одну тему. Если после второго круга
     существенные `rejected_tezisy` остались — идти в шаг 3 с тем, что
     одобрено, и явно отметить пробел в отчёте пользователю в конце
     пайплайна, а не зацикливаться.
3. **`garden-article-writer`** — вход: тема, `slug`, `approved_tezisy`.
   Выход: файл `docs/articles-src/<slug>.md`.
4. **`garden-illustrator`** — вход: `slug`. Выход: `docs/img/articles/<slug>.jpg`
   + поле `image` во front-matter статьи.
5. **`garden-editor`** — вход: `slug`. Выход: точечные правки текста на
   месте + короткий отчёт, что поправлено/что спорно, подходит ли иллюстрация
   теме.
   - Если редактор пометил иллюстрацию как несоответствующую — вернуться к
     шагу 4 (`garden-illustrator`) с уточнённым промптом (что не так с
     сюжетом) и повторить проверку у редактора, прежде чем идти дальше.
6. **`garden-article-builder`** — вход: (без параметров, работает по
   изменённым файлам). Выход: пересобранная статика + `git diff --stat`.

## Перед запуском пайплайна

**Уточнить тему и `slug`.** `slug` — латиница-транслит через дефис
(`zelenoe-cherenkovanie`). Проверить, нет ли уже `docs/articles-src/<slug>.md`
— если есть, это правка, а не новая статья (для точечной правки существующей
статьи можно пропустить шаги 1–2 и сразу дать `garden-article-writer` и
дальше по цепочке уточнённый бриф, без полного цикла исследования).

## После пайплайна

Показать пользователю: итоговый `git diff --stat`, отчёт `garden-editor`,
что осталось спорным (если есть `rejected_tezisy`/пометки агронома). Не
коммитить и не пушить — это делает скилл `garden-release` по отдельной
команде.

## Куда сохраняется результат

- Источник: **`docs/articles-src/<slug>.md`** — редактируется субагентами
  `garden-article-writer` (создание) и `garden-editor`/`garden-illustrator`
  (точечные правки текста и front-matter).
- `docs/img/articles/<slug>.jpg` — иллюстрация от `garden-illustrator`.
- `docs/articles/<slug>.html`, `docs/articles/index.html`, `docs/sitemap.xml`
  — **сгенерированы** `garden-article-builder`, руками не трогать.

## Границы

- Никогда не публиковать агротехнический факт без веб-подтверждения
  (`garden-researcher`) и климатической сверки (`garden-agronomist`).
- Не редактировать сгенерированный HTML.
- Не коммитить в рамках этого скилла.
